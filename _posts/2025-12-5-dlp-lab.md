### Introduction

The purpose of this exercise is to experiment with setting up a Data Loss Prevention (DLP) lab in my home environment. I previously was in a role that was dedicated to DLP, but when I came into that role much of the infrastructure and basic rule sets were already implemented for detecting information. I figured creating this test environment and testing out rule sets would be a good way to understand what goes into creating these systems, but also lets me to further improve my skills in this area.

If you are not familiar with Data Loss Prevention, according to Microsoft it can be described as "Data loss prevention is a security solution that identifies and helps prevent unsafe or inappropriate sharing, transfer, or use of sensitive data. It can help your organization monitor and protect sensitive information across on-premises systems, cloud-based locations, and endpoint devices. It also helps you achieve compliance with regulations such as the Health Insurance Portability and Accountability Act (HIPAA) and General Data Protection Regulation (GDPR)." (Source: [https://www.microsoft.com/en-us/security/business/security-101/what-is-data-loss-prevention-dlp)](https://www.microsoft.com/en-us/security/business/security-101/what-is-data-loss-prevention-dlp)). The basic idea being you want to understand where in your environment sensitive data lives, and then implement security controls around it so only those who have a need have access to it and track what actions occur on these files and data. If you see suspicious actions such as sharing or copying of the data and then the exfiltration of the data outside of the environment, you can investigate this to understand if it is an insider threat or if it is part of normal business operations. In small environments this can be generally easier in you might only have a few servers that store data, but in large environments this becomes much harder with many teams operating across multiple locations with their own processes or with shadow IT storing in unapproved locations.

### General Environment Setup

For this lab, the general setup I came up with through research is to have a single file server running Samba which will contain the files with fake sensitive data such as credit card data, social security numbers, etc. and then I can use my Windows PC to interact with these files. Additionally on the file server will be running open source DLP or detection software to detect the sensitive data in transit, and then possibly detect actions take on the sensitive files (depending on how easy this is will be down now or later when time permits). For this lab I will also just generate an alert that a sensitive file has been detected which I will send to Gotify since that has already been setup in my environment.

### File Server Setup

Setting up the file server involved creating a new Ubuntu slim server and then installing Samba by running `sudo apt install samba -y`. This installs Samba but doesn't configure a location to act as a fileshare at all or the permissions around that. Created a folder location by running `sudo mkdir -p /srv/share` and the setting its permissions open to everyone through `sudo chmod -R 777 /srv/share`. This only creates the fileshare location but nothing is configuring Samba to use it as such. To finally have it open to other clients and really become a fileshare, the Samba configuration needs to be modified which I did through nano `sudo nano /etc/samba/smb.conf`. In the file I scrolled to the bottom and added this block:

```
[DLPShare]
   path = /srv/share
   browsable = yes
   read only = no
   guest ok = yes
```

After saving the file the Samba service was restarted to have this change take effect. I then verified that the fileshare was now open by connecting to it from my Windows PC and then creating an empty file called `test.txt`

Now originally all I was going to do was install Snort on the fileserver itself and create and run the rules there to detect the traffic, but after doing some research I found out that pfSense firewalls can have Snort installed on them and you can run and manage rules there. I already have a pfSesne firewall created and configured to segment my main network from a malware analysis network so I decided to use that for this. I modified the VM to switch to this separate network, which also meant that now it was in a different IP subnet. To fix it so I could still connect to the fileshare server I had to modify my home router to have a static route when going to `10.10.10.0/24` to route it to the pfSense firewall IP that is exposed on the `192.168.0.0/24` home network. Additionally I then had to create a few new firewalls rules that just basically allow all traffic between the 2 networks and also to allow bogon networks since by default pfSense blocks these networks from talking. This took a few hours of trial to get this all figured out, and also found a weird issue with what IPs were being assigned in the malware analysis network, but once everything was working I was able to connect back to the fileshare server now on `10.10.10.2`.

### Rule Creation and Testing

For the purpose of this lab, I am only looking for very basic rules that will trigger on the contents of the file. The first step in this is to first create an interface for Snort to monitor the traffic on. Before this Snort was installed on the pfSense firewall but it wasn't looking at any of the traffic.

![](/assets/img/dlp-lab/vLsimage.png)

I kept everything as the default options for the moment due to just testing, and not needing any alert to be put in the Systems Log or capturing the packet for later investigation. With this created though traffic on my malware analysis network, or vnet1, is now also being passed to Snort but still no logic or rule is being run on the traffic. For that I had to go to LAN Rules and here it automatically selects the custom.rules file that can be edited.

#### Keyword Rule

![](/assets/img/dlp-lab/9qeimage.png)

Normally if there is nothing there right away but as can be seen above I have 1 rule in there that was created for initial testing. The full rule is `alert tcp $HOME_NET any -> any any (msg:"Sensitive data keyword detected in SMB"; content:"confidential"; nocase; sid:1000103; rev:1;)` and what it does is it looks at TCP traffic originating from the malware analysis network on any port and is outgoing to any other network and to any port and looks to see if the content of the file contains the phrase "confidential" in it. If it does then an alert is triggered for Snort with a message that "Sensitive data keyword detected in SMB" with a unique identification code associated in that rule defined in the `sid` parameter. Technically this rule is a bit more broad then what you would really want if looking for if you wanted to inspect Samba traffic specifically as this looks at all ports and not only ports 445 and 139, but again since this is a testing phase I usually go very broad and then narrow rule sets to be more specific once I know everything is working. For creating and understanding the Snort rule I used the official document at [https://docs.snort.org/rules/](https://docs.snort.org/rules/) and then additionally used AI to speed up the process and verify my understanding of the rule was correct.

Attempting to trigger the rule now would be a simple test of copying the file from `DLPShare` to my local machine. I added "confidential" to be the only thing in the text file and then copied the file locally to my desktop and then went into Snort to see if an alert had been triggered which one had.

![](/assets/img/dlp-lab/Hhbimage.png)

This looks exactly like what I would expect based on the rule I had created previously with the proper alert message and SID number. This was a positive step forward in verifying that the rule was working as expected, but I wanted to continue with testing out Snort rules and make sure I understand them a bit better.

#### Regex Rule

For this next phase of testing I wanted to focus on trying out some regex rules for detecting data. In a real world environment this is a much better way of detecting confidential data because instead of looking for a keyword, like in the first example, which could be changed or removed from a file regex looks for a pattern in the data. These patterns, such as Social Security numbers or credit card numbers, are static and will always be known to everyone so we can look for these patterns so even if keywords or phrases such as "credit card list" are removed from the original file we can still trigger on the data itself.

The following rule was added onto the custom.rules file within pfSense `alert tcp $HOME_NET 445 -> $EXTERNAL_NET any (msg:"Possible SSN exfiltration"; pcre:"/\b\d{3}-\d{2}-\d{4}\b/"; sid:1000001; rev:1;)`. The main difference between this rule and the original rule is that:

1. This time I did restrict the originating port to only be 445.
2. I used the [PCRE ](https://docs.snort.org/rules/options/payload/pcre)option instead of the content option, to create a regex rule to detect against the packet data.
3. The regex rule is configured to look for a social security string that is composed of 3 numbers, a dash, 2 more numbers, a dash, and then 4 more numbers with no other characters before or after the string.

Testing this rule I followed the same procedure as before of creating a new file, this time calling it `Important Document.txt` and putting in a fake social security number of "000-00-0000".

### Conclusion

This overall was good lab experience for myself. I got to test out these alerting rules in a very limited fashion, but it gives me a good understanding of what the setup looked like and how I can create and improve rules in the future for doing more in-depth testing.

Even though this was a good experience, this was also not overly realistic in what you would see in a real world enterprise environment. Firstly my fileshare was set to be unencrypted so that pfSense and Snort would be able to analyze the packet data, but in a real world environment you would never want this setup that way even if it wasn't publicly exposed to the internet. To enable this type of detection you would either have a proxy that all traffic goes through first before going through the firewall which would allow the firewall to analyze the data and then re-encrypt it, or you would use a next gen firewall which can do this in a single solution of SSL inspection. This could be another lab for me to try out as but for just trying out new rules this would be sufficent.
